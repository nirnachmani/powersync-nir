# Complete Shared-EV Migration Across App and Dashboard — Implementation Plan

> **For Hermes:** Planning only. Obtain the user's agreement on the proposed architecture and migration policy below before implementing. Use small, focused implementation slices; do not deploy or operate the charger without separate authorisation.

**Goal:** With a shared Generic Charger or Sigenergy EVAC binding active, show and control only the selected logical EV, never an extra charger-as-EV; preserve accurate physical measurements, site load, historical data, and safe fallback when vehicle identity is unknown.

**Architecture:** Keep `generic_ev` / `sigenergy_charger` as *internal physical runtime/loadpoint IDs* for leases, metering and charger I/O. Project a stable logical `vehicle_id` (`shared_ev_profile_a` or `_b`) and configured name/SoC onto all public EV surfaces from the authoritative selector, using one common pure projection function. The Android app is immutable: preserve existing routes, response field types and command vocabulary, and make every app-consumed read/write surface use those logical IDs. Leave old stored settings untouched but inactive and invisible as an EV while shared binding is active; do not copy settings between records as part of this display/control fix.

**Tech stack:** Home Assistant Python HTTP views/sensors/automations, existing frontend JS, pytest and small Node VM tests.

---

## Why this was missed

I planned and tested the selector-to-command guard and `/ev/vehicles` projection as if they were the full migration. I failed to inventory the *other consumers* of vehicle identity: the canonical `/ev/loadpoints/status` snapshot (which also feeds widgets and HA sensors), app EV Quick Charge and boost paths, `/ev/vehicle_config`, Smart Schedule's separate executor storage and endpoints, and dashboard control IDs. The previous dashboard fix checked only disabled **charger backends**; Generic Charger stays enabled, so that rule cannot hide its obsolete *vehicle*. These are design/coverage omissions, not something that would have been prevented by running a larger unrelated test suite.

## Evidence and assumptions to validate before implementation

- Current binding resolves `tank_500` to A; physical Generic remains enabled. `/ev/vehicles` already returns A and B without `generic_ev` (see `tests/test_shared_logical_vehicle_api.py`). Legacy `generic_ev` config and disabled schedule remain persisted. Current status snapshot/HA EV sensors label the same car `generic_ev` / `EV`.
- `EVLoadpointStatusView._async_build_response()` in `custom_components/power_sync/__init__.py` constructs the Generic observation from its old record; `_get_ev_display_coordinator()` publishes that snapshot to `/ev/loadpoints/status`, `/ev/widget_data`, and HA sensors through `ev_display.py`. Dashboard controls currently send `loadpoint.loadpoint_id` in command/boost requests. `AutoScheduleStatusView` and `AutoScheduleSettingsView` serialize executor `_settings` without filtering the legacy key. `VehicleChargingConfigView.get()` returns persisted configs without filtering.
- The existing static Android contract establishes `/ev/vehicles` and command ID behaviour, and lists `/ev/widget_data`, `/ev/boost`, `/ev/vehicle_config`, and auto-schedule routes. It does **not** prove which response/call site supplies the app's EV Quick Charge *label* or which ID it sends when pressed. Before changing an endpoint, do one bounded trace of that screen against the existing released-app notes/fixtures; only if inconclusive, obtain one sanitized read-only app observation (no button press). Do not guess that altering `/ev/loadpoints/status` alone fixes the app.
- **App/dashboard Smart Schedule difference:** Released-app static analysis in `docs/private-fork/android-multi-vehicle-feasibility.md` says the app Smart Schedule uses a selected `vehicleId` and `display_name` from vehicle records; `/ev/vehicles` already projects A/B without a third Generic EV. The dashboard instead directly enumerates `autoStatus.settings` in `_visibleSmartScheduleEntries()` (`frontend/power-sync-strategy.js`); `AutoScheduleStatusView.get()` exposes every stored executor setting, including disabled `generic_ev`, and its filter retains this row because the Generic *charger backend* is enabled. This explains why the extra row appears only on the dashboard. The precise app-side filtering call site was not preserved in the static fixture, so do not infer from this observation that the app's auto-schedule endpoint has no stale key; confirm that narrowly only if changing that endpoint is actually necessary.

## Proposed decisions for approval

1. **Two stable EV profiles remain visible in the app's vehicle list and Smart Schedule** (B is a disconnected placeholder until a second car exists); only the selected profile receives the charger's plug/charging/power. `none` (known unplugged), `unknown` (not enough evidence), unmapped or stale selection all mean **no EV can be selected for a command**; none defaults to A, even if power is flowing. A/B SoC comes only from their configured per-profile sensors; no generic SoC fallback.
2. **One physical charger remains one physical loadpoint internally**, with `loadpoint_id` unchanged. Public loadpoint status carries `vehicle_id` and `vehicle_name` for the selected logical profile; keep any physical ID only as charger/loadpoint metadata, not an additional EV. With no valid selection, preserve measured site/charger power but do not attach it to A/B or expose `generic_ev` as a controllable EV; disable all profile commands. `none` means the selector reported disconnected; `unknown` is *not proof of disconnection* (the sensor may be unavailable); if observed power conflicts with either state, show unassigned charger activity in diagnostics rather than a false car identity. Do not convert unknown readings into zero or hide physical energy use.
3. **Old stored records are not a second EV.** Here “legacy data” means the existing `generic_ev` vehicle-configuration record, its disabled Smart Schedule record, and past session records—not an active charging mode to migrate. Leave them in storage, unchanged, for backward compatibility/rollback and history. When binding is active, do not present the old config/schedule as an EV or execute its plan; old IDs must not be emitted by the app/dashboard as selectable command targets. Reject even a stale/cached direct write to that ID at the server boundary. Do not unnecessarily alter the app's Smart Schedule response just because its dashboard counterpart includes a stale setting. An unexpectedly *enabled* legacy plan is a conflict to report/stop from executing, not something to silently migrate, delete, or newly enable.
4. **No settings copy or activation in this fix.** Do not copy any old config/schedule settings to A or B, change current mode enabled flags, modify targets/departure times/capacity/policy, or rewrite sessions. A separate review of any user-requested setting migration can happen later. The plan addresses identity, presentation and command routing only.
5. Manual/app Quick Charge, Boost and Smart Schedule write paths must carry a logical profile ID through the existing guard. Generic physical IDs and `_default` must not bypass an active binding. Do not alter closed app code, controller maths, charger I/O semantics, or unrelated providers. Legacy unbound mode remains unchanged.

## Scope boundaries / ramifications

- Public `power_sync` namespace and app routes stay unchanged; no new Android build. Generic Charger remains enabled as a hardware backend. Physical diagnostics may still identify `generic_ev` internally, but app-facing EV lists/widgets/controls must not show it as a third EV.
- Existing sessions retain their original attribution; do not rewrite history to Tank. Only new sessions after correct selection use the logical ID. Runtime ownership and measured watts remain keyed by one physical loadpoint; no cloned A/B power or competing leases.
- Both `none` and `unknown` have no selectable EV and permit no profile-directed commands. `none` reflects a confirmed unplugged selector reading; `unknown` means identification is not reliable, which does **not** prove the charger is empty. If physical charging is nevertheless observed, make the discrepancy visible as unassigned charger activity, prevent profile commands, and keep energy totals correct; external-session policy remains subject to the existing fail-closed guard.
- An enabled legacy schedule or active legacy manual session is a migration conflict. Detect and surface it; do not silently stop an active charger, hide an executing plan, auto-enable A, or erase rollback data. Resolve at a separately authorised idle window.
- If the released app's Quick Charge uses an unmodifiable hard-coded label/physical ID that cannot be changed through a compatible response, report that constraint before implementation rather than claiming parity. Prefer the smallest compatible server-side adapter only if its safety and command identity can be demonstrated.

**Agreed scope from user feedback:** Keep placeholder B. Do not copy any old settings to A/B or change active charging modes. App/dashboard must offer only logical EV IDs as command targets; if no selected EV, commands are unavailable. Keep old records out of view while bound, but do not delete them or rewrite session history. The app's Smart Schedule currently displays only A/B, so target the dashboard discrepancy rather than changing app schedule payloads without evidence. Physical Generic remains available internally as the single charger; stale direct requests to its old EV ID are rejected for safety.
