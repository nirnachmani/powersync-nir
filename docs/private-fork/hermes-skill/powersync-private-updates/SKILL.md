# PowerSync Nir upstream maintainer

Integrate applicable upstream changes into `nirnachmani/powersync-nir` autonomously. This is an upstream integrator, not a general PowerSync auditor. Do not delegate the normal maintenance cycle to subagents: assess, implement and verify each change yourself. Keep work within `/home/nir/PowerSync` and registered candidate worktrees. Preserve an existing dirty candidate and the ledger when resuming.

## Decision for each upstream commit

Process commits strictly oldest to newest. Before making a candidate or running interaction tests, examine the actual upstream diff and answer, in order:

1. **Outcome:** What specific bug does it fix or enhancement does it provide? Identify its actual feature and hardware/provider gates; a shared filename does not make a vendor-only feature global.
2. **Relevance:** Does the outcome affect global functionality, Sigenergy, Amber, solar/site flows, the supported Generic or Sigenergy EVAC charger, or the fork's shared logical EVs? Reject unsupported-vendor/provider-only outcomes with a concrete reason. Keep existing AI explanation providers in scope even when not selected, including approved ChatGPT sign-in and follow-up changes; the user may switch AI providers. Review their actual authentication and credential-storage boundaries; optimiser licensing remains excluded.
3. **Need:** Does the fork contain the affected behavior and problem, or would the enhancement apply? If the fork already implements the outcome, record `rejected` with the explicit reason `already covered by fork` and cite evidence; this is not a rejection of a useful upstream fix. The ledger has no `redundant` outcome.
4. **Port:** Apply the relevant upstream behavior as written when compatible. If it overlaps fork-specific code, adapt it to deliver the upstream outcome while preserving the fork's actual invariants. The maintainer may extend the immediate implementation as needed to make that update work safely without asking. Keep changes and tests as narrow as the outcome requires.
5. **Scope:** Fix new regressions caused by the update. A pre-existing issue merely noticed during review is out of scope; note it if useful, but do not turn the cycle into a general audit or independent repair. If a pre-existing issue genuinely prevents delivering this update safely, first find a narrow compatible adaptation rather than treating discovery as a reason to stop. Do not weaken required gates or silently overlook a demonstrated material incompatibility.
6. **Record and advance:** Record `ported`, `amended`, `rejected`, or `admin/no-port` and a factual reason through the ledger CLI, then process its next commit. Administrative release/version/docs bookkeeping is `admin/no-port`. Do not invent a new outcome or record unfinished work.

Do not reassess upstream product choices on inherited features, invent upgrade migrations merely to retain old upstream defaults, or solicit approval for ordinary implementation choices. Ask the user only when the available safe approaches have a significant user-facing functionality, architecture, activation-limit, or security implication that requires their choice. Explain the concrete consequences and alternatives. Genuine missing access or an enforced runtime limit is an operational interruption, not a product decision.

## Fork and security boundaries

- Read `docs/private-fork/local-change-inventory.md` for the fork's actual changes. Preserve the HA domain `power_sync`, existing Android `/api/power_sync/...` contracts, independent logical EV settings and SoC, selected-profile guard, one physical shared charger and its lease/session/stop-handoff behavior. Scope chargers to Generic and Sigenergy EVAC; do not expand compatibility for Tesla, EVDC, OCPP or Zaptec.
- Preserve fork-specific Sigenergy export-limit ownership and fork-only HACS update targeting. For a settings/UI change, trace the affected action through the actual device or installation boundary; don't assume a UI-only port cannot affect it.
- Exclude upstream remote-support diagnostics, external support brokers, remote access and remote sharing of diagnostic data or archives, including later fixes and follow-ups for those excluded capabilities. Record remote-only changes as `rejected` with the owner's decision as the reason; do not ask the owner to make that same decision again. Assess separable local-only diagnostics and unrelated improvements normally, and port them only if independently relevant and safely separable from remote support. Review mixed commits by actual behavior and hunks, not merely filenames or references to diagnostics.
- Never wholesale merge/rebase upstream 1404+ or import optimiser licensing, entitlement gates, subscription UI, `optimizer_access`, `subscription_required`, `LicensedBatteryController`, or hosted licence dependencies. Licensing imports, guards and pairing are excluded; hosted API entitlement and permission services and subscription UI, storage, recovery and fences are excluded. For the optimiser, manually review each hunk; licensing-coupled hunks are incompatible until disentangled. Preserve upstream source attribution and noncommercial scope. Assess mixed licensing-adjacent commits hunk by hunk: retain separable relevant non-licensing improvements. Preserve upstream attribution and licence notices.
- Push only to approved `nirnachmani/powersync-nir`, never to upstream or with force. Never expose credentials, tokens, device addresses, or captures in reports or commits. Never deploy, restart Home Assistant, edit its `.storage`, or operate physical devices: deployment requires separate authorisation.

## Cycle and verification

1. Confirm the approved origin fetch and push URLs, source branch, clean or explicitly recorded worktree, private head and ledger checkpoint. Fetch upstream and pin the target SHA for this cycle. Reconcile published fork changes before editing; never overwrite a newer published branch or an unfinished candidate.
2. Use `scripts/private-fork/maintainer_ledger.py --repo /home/nir/PowerSync next --state <ledger> --target <pinned-target>` for the exact next commit; `record` each terminal outcome with version, reason, and reachable private commit SHA where required. Use explicit `refs/remotes/upstream/main` when pinning; a short upstream ref may be ambiguous. The schema-versioned ledger is the sole checkpoint: do not write freeform checkpoints or use `maintainer_cycle.py` on it. At merge branches let the ledger enumerate every unrecorded commit; do not substitute a simple first-parent range.
3. Run focused tests for the upstream outcome, the fork-specific adaptation and any new regression caused by the change. Do not use broad suites to hunt unrelated upstream or unsupported-vendor problems. Run `scripts/private-fork/validate_local_architecture.py` and `scripts/private-fork/run_private_tests.sh` once on the final candidate before publishing; establish the starting baseline if needed to distinguish a failure. Do not repeat full gates for each ordinary commit. Do not use an integration helper that wholesale merges upstream.
4. A failed gate blocks publication, not investigation. Diagnose and correct the port or review and narrowly update the relevant test expectations; continue without asking about ordinary implementation details. Never bypass, weaken, delete or misreport a failing test. For source-continuity checks, review the intended source delta and protected invariants, extend only its exact approved lineage and retain mutation-rejection tests. Never blindly refresh a fingerprint.
5. Continue until `next` reports no remaining commits through the pinned target. A partial backlog, subtask boundary, or failed check is not a completed cycle. If a real enforced limit or unrecoverable external failure interrupts the work, preserve the candidate, ledger checkpoint, target, next commit and evidence; report the operational interruption and arrange safe immediate continuation if supported. Never invent a limit or claim a follow-on was started without verification.
6. When applicable changes were integrated, the pinned target is exhausted, and required gates pass, set a unique fork version/tag of the form `v<latest-fully-processed-upstream-tag>-nir.<serial>`, commit release metadata, fast-forward and push `feature/shared-logical-evs` and `main`, create a GitHub release, and verify remote branch, tag, release and manifest. Do not publish a rejected/admin-only cycle, incomplete work, or a failed gate. Publication is not Home Assistant deployment.

## Report

The existing per-update Markdown table must appear in the email body and detailed report for every processed commit: upstream version/commit, outcome, and brief reason or amendment. Give actual gate, commit, publication and deployment status. When the run stops, explain a blocker in plain language: what the feature does, the issue, its practical implication, what was attempted and whether a user decision is actually needed. Do not imply unverified hardware failure or make a routine partial backlog sound like a product decision. Send the report with the configured Resend tool using the approved server email defaults; a send acceptance is not proof of inbox delivery. If sending fails, retain the report and state that it was not sent.

## Skill synchronisation

The tracked `docs/private-fork/hermes-skill/powersync-private-updates/SKILL.md` is canonical. After an authorised update, install it into the named `powersync-maintainer` server profile with `scripts/private-fork/install_maintainer_skill.sh` and verify the server checkout, installed skill, local skill and GitHub source match. A repository push alone does not update the profile-local skill.
